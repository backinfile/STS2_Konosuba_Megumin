# Spine 动画制作指引：先画动作，再绑定和换图

适用项目：惠惠《杀戮尖塔 2》模组。更新于 2026-10-10。

本指引以 Spine 官方教程、本地《杀戮尖塔 2》原版角色数据和本项目 v6 的失败为依据。制作顺序固定为：**参考图与动作设计 → 部件及角度变体 → 姿势绑定 → 关键帧 → 中间过程 → 对照验收 → 导出**。

## 1. v6 为什么不能作为动作合格的依据

v6 的循环端点、IK 和接地数值通过，但用户明确判定动作不对。它没有先建立经检查的逐帧绘图依据。正面头身的横向压缩不能替代侧面透视；站立身体的整体旋转不能替代伏身、撑地和趴姿；骨骼握点连续也不能证明画面中持杖的是同一只手。进一步围绕错误动作调角度，只会让错误更稳定。

因此后续数值检查只验证结构与接入，**不得再以“测试全部通过”替代姿态、透视、重心和表演的视觉验收**。

## 2. 必须区分的四种方法

| 方法 | 适合 | 不适合 |
|---|---|---|
| 骨骼平移、旋转 | 同一视角下手臂摆动、重心移动、头部点动 | 把正面直接转成侧面 |
| 蒙皮网格变形 | 袖口、披风、裙摆、有限幅度的体积调整 | 把站姿网格拉成长距离趴姿，扭曲五官 |
| 同槽附件切换 | 同一只手的张掌/握拳、同一躯干的不同透视 | 用切换掩盖左右手归属变化 |
| 独立姿势绑定 | 前倾、坐跪、趴地、强透视手臂等大幅动作 | 为每个新角度无节制复制整个骨架 |

一个部位可以并且通常需要多张图。图的大小不必相同，关键是它们的**关节锚点、透视、体积与切换时的轮廓**能够衔接。原版和官方范例都混合使用骨骼、网格、附件和图层顺序。

官方依据：[新增姿势与附件工作流](https://esotericsoftware.com/blog/Rigging-new-poses-tutorial)、[不同姿势中的网格绑定](https://esotericsoftware.com/blog/Mesh-binding-tutorial)。

只读检查了本机 `D:/Github/spire-codex/extraction/raw/animations/characters/` 下的原版角色，不将 Watcher 模组当作原版。所检查资源的导出版本均为 **Spine 4.2.43**；这是本地资源版本，不代表已验证用户当前安装版本。

| 原版角色 | 骨骼 | 插槽 | 含多个附件的槽 | 可直接借鉴的设计 |
|---|---:|---:|---:|---|
| ironclad | 84 | 71 | 12 | `bod` 与 `attack/bod attack`；攻击用脚、小腿、膝盖；死亡用小腿、膝盖 |
| silent | 141 | 56 | 4 | 后臂、后手有不同图；`hand_l` 可在普通手与 `shiv_hand` 间切换 |
| necrobinder | 135 | 63 | 5 | `r hand` 有张掌、普通手、施法手；`l sleeve top` 有 `sleeve_l_extended` |
| regent | 103 | 81 | 7 | 上下臂的翻面附件；普通手、拳、惊讶手；多种眼睛 |
| defect | 101 | 69 | 4 | 左右施法拳与普通手；局部特效序列 |

“多个附件的槽”按已解析皮肤统计，**不包括所有借助独立槽显隐完成的姿势切换**，因此不能把它当作全部替换图数量。

死灵契约师 `attack` 的实际例子：

- 0.000 秒：右手显示 `open_hand`，左袖显示 `sleeve_l_extended`。
- 约 0.167 秒：右手换成 `r hand`，同时显示独立手指；左手切到背面手指组合。
- 0.600 秒：右手恢复张掌，左袖恢复 `l sleeve top`。
- 文件还保留 `_ignore/extra_assets_pose` 与 `_ignore/sleeve_rigging_pose` 两个辅助姿势。
- `die` 在约 1.033–1.100 秒启用 `death/...` 的肩、袖、胸腔、裙和头骨绘图，并隐藏对应站立部件。

这说明大动作既会在同槽中换图，也会启用专门的姿势部件组合，且切换与骨骼运动、遮挡共同设计。

## 4. 先做逐帧参考图

先独立确定待机、吟唱终姿、释放、撑地、趴地和恢复站立等姿势。之后才补动作之间的分解帧，并记录每张图对应的时间。绘图采样率与运行时刷新率是两回事：可以先以较低绘图频率确定动作，再由 Spine 插值；不能把自动生成的 60 个数值采样声称为 60 张已设计的参考图。

每张参考图必须检查：

1. **一个角色、一根杖、两只手、两条腿。** 批量图中出现残留旧杖、重复手臂的帧直接淘汰。
2. 身份连续。使用角色自身左右，而非画面左右；眼罩、绷带、握杖手不交换。远侧眼罩可以因透视被遮住。
3. 固定相机、地平线、头身比例与道具尺寸。不要逐帧自动居中缩放，否则会隐藏角色漂移。
4. 重心先转移，支撑脚再变化。腾空脚和支撑脚的任务要明确。
5. 杖的握点在杆上固定，整根杖是刚体。对比尖端、尾端、手掌位置；不能只看手掌是否挨着某个点。
6. 逐张看得通，按顺序播放也看得通。中间帧不能因为自身好看而偏离运动弧线。

输出应有：原始参考 PNG、提示词、逐帧时间表、锚点标注、淘汰原因。先修参考图，不能让骨架去迁就错误绘图。

### 4.1 生成图片必须执行去 AI 摩尔纹流程

每张新生成或重新生成的参考图、部件图和道具图，必须先执行去 AI 摩尔纹流程，再进入切图、绑定和图集导出。继承旧版本图片时也必须有可追溯的检查记录，不能因图片已经存在而跳过。

使用 [Mi-Ripple](https://github.com/miyang-ai/Mi-Ripple) 的原尺寸本地流程：保留原图和哈希 → 诊断周期网格、颗粒与鳞片状纹理 → 按诊断选择局部处理 → 查看热点图和原生像素对比 → 决定采用结果或保留原图。不得先缩放、压缩或截图再诊断。透明部件必须逐像素验证 alpha 通道保持一致；头发、轮廓线、眼睛、衣服装饰不能因降噪变糊或缺失。

保存工具版本、输入/输出哈希、诊断 JSON、处理记录和对比图。诊断未发现目标伪影时，记录“已检查，保留原图”，不能声称“已去除”。检测到与真实图案混杂的纹理时人工复核，不得盲目增强滤波。任何图片像素变化都要重新生成图集，并重跑动画与游戏渲染检查。

## 5. 惠惠需要的部件变体

| 部位 | 需要的姿态/角度 | 锚点与注意事项 |
|---|---|---|
| 头脸 | 正面偏转、三分之二侧面、侧面、低头、趴地侧脸 | 颈根、下巴、眼线；不能把正脸压扁成侧脸 |
| 帽子 | 原视角、转向、低头/伏地角度 | 与头顶关系稳定；帽檐透视要跟随头 |
| 躯干与裙 | 正面、侧转、前倾、跪撑、趴地 | 肩、腰、髋、裙摆落点；前后不能翻反 |
| 右上臂/袖 | 下垂、内收、前举、透视缩短、撑近地面 | 同一右肩；袖根遮住接缝 |
| 右前臂/握手 | 竖杖、中间斜杖、横向送杖、伏地持杖 | 同一中段握点；拇指与掌背方向正确 |
| 左臂/手 | 放松、后摆、张掌、接地撑掌、抬掌 | 左掌接地后先保持世界坐标再抬起 |
| 腿与靴 | 正常、迈步、屈膝、跪撑、趴地伸腿 | 绷带归右腿；鞋底接触不能只看脚踝骨 |
| 披风与头发 | 站立、转身滞后、前倾、覆背趴地 | 顺重力与运动滞后，不能用固定跟随代替 |
| 表情 | 专注、吟唱口型、释放、受击、疲惫闭眼 | 限定局部替换，不改变整个脸宽和眼位 |
| 法杖 | 原刚体为主；只有真实透视变化才用角度图 | 固定杆长与握点；不得为了让手够到而拉长 |

不要机械地给所有部位准备同样数量的图。参考图暴露了新表面、遮挡或严重变形，才新增相应附件。

## 6. 拆图与绑定的顺序

每个部件应有透明背景、足够的关节遮挡余量和明确的枢轴。不能把完整姿势粗切成互不重叠的拼图后直接旋转：接缝后方没有绘图，运动时就会露洞。需要补画被遮挡的肩、肘、腰、髋及衣服内侧。

新增姿势应保存为可复用的绑定姿势，例如 `bind/turn_45`、`bind/arm_forward`、`bind/brace`、`bind/prone`。先把骨骼摆到参考图对应的位置，再对该姿势的网格进行绑定；绑定后才调权重。**不要在站姿绑定趴姿网格，再期待旋转骨架自动得到正确趴姿。**

官方流程可先将新网格临时绑定到不会运动的根骨，再在动画姿势中调整骨骼并重新绑定。改变权重时若顶点突然跑位，优先检查绑定姿势，而不是继续补偿位移。相关工具为 `Update Bindings`。[网格绑定教程](https://esotericsoftware.com/blog/Mesh-binding-tutorial)

## 7. 骨架是为动作服务的

建议骨架层次：根/整体位移 → 骨盆 → 胸腔 → 颈/头；双臂分别保留肩、上臂、前臂、手；双腿保留髋、腿、膝下、脚；披风、帽尖、发梢用少量辅助骨。武器根与右手握点有明确的主从关系。

IK 适合接触约束，FK 适合自然运动弧线，允许分段混合。手握杖、脚踩地、手撑地是三类不同约束，不能用一组固定 IK 参数包办所有状态。改变弯曲方向必须经过可解释的伸直或透视换面，不能在深屈曲时跳到另一解。

二维骨长是屏幕投影。透视缩短时可调整子骨距离，并配套角度绘图；不能一方面要求投影骨长完全固定，另一方面又要求真实转身。仅靠把面片横向缩小得到的假侧面也不合格。

## 8. 附件切换怎样不跳

先把两张附件的关节锚点、外轮廓与可见体积在切换姿势对齐。再把附件键放到遮挡变化、运动速度较快或正好经过相似轮廓的时刻，同时调整骨骼、网格和前后层级。

重点检查切换前一帧、切换帧、后一帧，以及它们之间的运行时插值。用半透明叠图检查颈根、肩、腰线和眼位；差异大就补中间角度图。淡入淡出不是默认补救，它容易出现双眼、双轮廓和两根杖。

每个动作首帧显式设定必要的附件与图层状态，防止上一个动作留下来的张掌、死亡部件或背面头泄漏。附件、绘制顺序与事件是不同时间线，需要各自管理。[关键帧与附件、绘制顺序](https://esotericsoftware.com/spine-keys)

## 9. 惠惠本轮动作原则

**进入吟唱：** 从原右手持杖起点出发。头与视线先行，肩与髋跟随；右肘适度收回，把杖转到可前送的方向，再伸臂送到胸/肩高度。左手自由。准备姿势先在参考图上确认，避免再次用腰下横扫来凑终点。

**持续吟唱与释放：** 吟唱是已站稳的准备状态，只保留必要呼吸和口型；释放包含清楚的蓄力、发力与收住。伤害脉冲次数不应重播身体释放动作。

**脱力：** 从释放终姿开始卸力，屈膝前倾，左掌接地，胸腹伏下，披风覆背。终点必须清楚看出腹部朝地。不能先躺到背上再切成趴图。

**起身：** 从趴姿本身开始，先抬头、撑掌、收膝、抬髋、站稳、收杖。左掌仍承重时不能跟着胸腔滑走。是否有短暂停顿应由重量感决定。

**受击与死亡：** 按当前基础状态制作变体；倒地受击不能突然站立。死亡保持的绘图与前一段必须连续，循环与非循环状态由播放逻辑设置。

## 10. 验收必须同时有画面和数据

先做同时间、同尺度、同地平线的**参考图 / Spine 渲染并排页**，再提供透明度叠图与轮廓模式。标出每帧使用了哪些部件变体。至少检查原速、0.25 倍速、逐帧、附件切换邻域和实际游戏显示尺寸。

画面验收项目：姿势与参考是否相符；持杖手是否可追踪；胸腹与背面是否正确；头身比例是否漂；关节是否脱节；道具是否伸缩；鞋底与手掌是否接地；披风是否穿过身体；在中间帧能否看出动作意图。

数据验收项目：运行库可加载；附件存在；首帧复位完整；坐标有限；循环及衔接稳定；事件次数正确；接触点误差；骨骼/网格变化是否出现尖峰。投影角度与位移阈值只作异常筛查，不能证明自然。

### 10.1 必检：动作跳变与部件大小异常

- 固定相机、画面尺度和地平线，覆盖所有动作及动作间衔接；禁止用逐帧自动居中、缩放掩盖问题。
- 每个附件切换点保存前一帧、切换帧、后一帧，检查轮廓、衣纹、关节连接、遮挡及绘制顺序。以原速、0.25 倍速和游戏实际显示尺寸复看，不能只看关键姿势。
- 逐项检查头、帽、双手、双臂、躯干、双腿和鞋的大小是否突然改变，以及是否出现瞬移、拉长、折叠、脱节或额外肢体。透视变化必须有绘图依据，不能统一缩放所有部位来掩盖错误。
- 在运行时实际变形后的网格上，按源图 alpha 加权计算可见面积与重心；透明留白不能计入体积。比较切换点两侧极小时间间隔，并以 120 FPS 采样检查插值，排除正常运动速度的影响。
- 记录每个姿势的尺寸校准、关节锚点与绑定依据。头部和握杖手的稳定性单独设门槛；躯干、腿部的投影面积受遮挡影响，必须结合剪影和参考图复核，不能只套面积阈值。
- 本项目 v8 回归门槛：头部换图面积变化 ≤6%、重心跳变 ≤4 Spine 单位、同一附件头部面积漂移 ≤5%；握杖手换图面积变化 ≤1%、重心跳变 ≤1 单位；左手轨迹逐 60 FPS 帧位移 ≤20 单位。阈值用于捕捉已复现故障，不是自然动作的评分。不得为了通过而放宽阈值。
- 保存失败帧、时间、槽位、旧新附件、数值、原因和修正后的同位置截图。修复后重跑原始失败用例，并用游戏原生 Spine 渲染复查；浏览器预览通过不能替代游戏验收。

必须保存失败帧及原因。仅在实际渲染和参考图对照完成后才能把该版本标为完成。图片生成的序列同样需要筛选；不能因为工具生成成功就默认动作正确。

### 10.2 必检：节奏、弧线与跟随

位置连续、尺寸稳定只说明没有这两类故障，不能据此判定动画自然。还必须检查：

- 标明哪些姿势是停顿、接触或反向，哪些只是经过姿势。经过姿势不得因为统一缓动而机械地减速到零；真正的承重、停顿和撞击也不能为了“丝滑”被抹平。
- 在固定相机下追踪头、胸、骨盆、双手、脚底和杖尖的屏幕轨迹，查看等时间间隔的位置点、速度谷和方向突折。判断画面中的弧线，不只看骨骼局部曲线是否好看。
- 先确认重心与主动作，再处理头、肩、肘、腕及披风、帽尖的跟随。错开到达时刻必须符合动作因果，不能给所有部位机械地延迟同样帧数。
- 循环和动作衔接检查位置及速度；接触段检查支撑点滑动；附件切换检查外轮廓与内部线条。面积、重心相同的两张图仍可能发生视觉跳变。
- 保留相同相机、原速播放的游戏内前后对比录像，并区分录制掉帧与动画本身的停顿。慢放和数值报告用于定位，原速观感决定动作是否成立。

## 11. 导出与交付

运行库与编辑器主/次版本匹配。交付保留 JSON、atlas、纹理、部件源图、替换关系、关键姿势时间表、生成提示词、参考对照页、验证报告和重建脚本。真正经过编辑器保存才称为 `.spine` 工程；只有生成 JSON 时应明确写“可导入 JSON”。

原版素材只用作本地结构和动画研究，不混进惠惠的运行时图集。进入游戏前还需检查目标加载器、动画名/触发名映射、状态混合、实际显示尺寸与选择边界。

## 12. 官方学习路径

1. [Spine 用户指南](https://esotericsoftware.com/spine-user-guide)：骨骼、插槽、附件、关键帧、网格与约束的概念。
2. [关键帧](https://esotericsoftware.com/spine-keys)：附件键、绘制顺序、插值及运行时帧间位置。
3. [网格绑定](https://esotericsoftware.com/blog/Mesh-binding-tutorial)：在动作姿势中绑定，理解错误绑定为什么造成网格跳动。
4. [新增姿势工作流](https://esotericsoftware.com/blog/Rigging-new-poses-tutorial)：为新透视画图，建立替代绑定姿势，复用原骨架。
5. [官方制作直播索引](https://en.esotericsoftware.com/spine-twitch)：查找头部转向、2.5D 躯干、权重与多角度姿势实例。

本指引中的惠惠制作选择是结合以上资料与项目问题作出的设计判断；原版统计与切换时刻来自本地 `.skel` 解析报告。


## 13. v7 续做中的实证修正

不能把大量肩、肘、腕、膝和辅助点无区别地放入同一个全身变形网格。手腕从膝前抬到胸前时，这些点在二维投影中的相对顺序可能改变，导致腿和衣服一起折回去。v7 采用站姿连续权重与大姿势局部手臂/腿权重相结合；手掌切片必须包含完整手指，袖根保留重叠。

另一个实际问题是关键姿势相符、两张图之间却严重拉扯。因此除了原速与慢放，还必须检查**换图前一帧、换图帧、后一帧**及 120 FPS 的插值采样。替换键不一定都放在两张参考图时间的正中间；可比较两侧绘图在过渡姿势中的变形，选择一次稳定切换，再人工检查轮廓。

本次记录的失败包括转身牵扯衣服、起身时手腕牵扯腿部、按槽独立绑定后出现接缝、循环披风起点偏移，以及编辑器源图路径缺失。修正与剩余边界见 [v7 说明](../../actions-v7/README.md)，复查入口为 [参考 / Spine 对照](../../actions-v7/preview.html)。结构测试通过不等于动画美术已最终定稿。

## 14. v8 体积跳变修正与游戏验证

v7 的独立绘图未校准可见头部大小，头部又受全身网格影响；转身左臂的分段插值还在中点产生位移突变。v8 按实际 alpha 面积校准姿势比例，将头部固定到可见重心并保留独立颈部连接；每张握杖手图保留自身角度，但校准大小和握点；左臂改为连续轨迹。腿部保留各姿势绘图，避免跨透视复用造成鞋子和裙摆残片。

复查见 [v8 说明](../README.md) 和 [项目内 Mod 测试环境](mod-lab.md)。离线连续性报告、原生游戏逐帧截图与战斗测试分别记录，不能把“角色可进入战斗”当作动画质量合格。

本地 v8 复查发现：

1. `build_actions_v7.py` 的 `interp_schedule` 对每段参考姿势统一应用 `u²(3−2u)`。该函数在段首、段尾导数为零，所以所有参考姿势都被当成停靠点；v8 仍继承这套节奏。
2. `interpolate_pose` 对各骨骼的世界位置使用同一个进度做直线插值。它保证端点相接，却没有自动建立手腕弧线、身体各部分的先后关系或重量感。
3. 大部分非道具槽位随同一个 `active` 姿势一起换图。头和手的面积校准解决了体积跳变，但不能保证帽檐、衣纹、裙摆等轮廓相接。

用本项目 `spine-core` 4.2.95 采样原生骨骼轨迹：`chant_enter` 在 0.60 秒处的右手速度约为 20 单位/秒，相邻两段峰值约 248；0.83 秒处约为 5，相邻峰值约 113.5。关键点速度用前后合计 1/60 秒差分估算，峰值在相邻区间取 100 个位置、以 1/600 秒差分估算。这是机械启停的定位证据，不能单凭速度比判定一个姿势应否停顿。

现有录像采集速率为 29.73–30.21 FPS，且已检查非黑屏和画面变化；因此应优先处理上述动作设计问题。该记录仍不能证明所有设备或播放环境都不存在掉帧。

后续修正顺序：先在 `chant_enter` 上标出停顿与经过姿势，修正主动作节奏和手杖轨迹；再修换图轮廓；最后加入有依据的身体跟随及披风收势。用原速游戏对比确认后，再推广至脱力、起身和其余动作。新增绘图仍必须先通过第 4.1 节的去 AI 摩尔纹流程。

### 16.2 最值得复用的技术经验：分开“编写格式”和“运行库格式”

仓库的 [`_convert_timeline`](https://github.com/GenielabsOpenSource/spine-animation-ai/blob/702b71689cac826efee942ee4564fef9560d6ef8/scripts/build_spine_json.py#L92) 和[格式参考](https://github.com/GenielabsOpenSource/spine-animation-ai/blob/702b71689cac826efee942ee4564fef9560d6ef8/references/spine-json-spec.md)已经处理了 Spine 4.2 的几个关键差异：

- 骨骼旋转时间线使用 `value`。不能把旧版的 `angle` 字段直接写入 4.2 动画。
- 在本项目 4.2 运行库中，骨骼贝塞尔曲线使用绝对时间和属性值控制点。归一化缓动只能作为编写参数，导出时按该段的起止时间与起止值换算。
- `rotate` 一个属性需要 4 个控制点数值；同时描述 x/y 的 `translate`、`scale`、`shear` 需要分别为两个属性写入，共 8 个数值。单独的 `translatex` 等则只有一个属性。
- 导出键上的 `curve` 控制从该键到下一键的区间。仓库内部简写把曲线放在目标键，转换时前移；这只是它的内部约定，不能对已经合规的 Spine JSON 再执行一次转换。

例如骨骼 y 从 0.4 秒的 10 移到 1.0 秒的 30，x 保持 0，使用归一化控制点 `(0.25, 0)`、`(0.75, 1)`，对应的 4.2 平移时间线为：

```json
[
  {"time": 0.4, "x": 0, "y": 10,
   "curve": [0.55, 0, 0.85, 0, 0.55, 10, 0.85, 30]},
  {"time": 1.0, "x": 0, "y": 30}
]
```

已用本项目 `spine-core` 4.2.95 做最小数值验证：上述例子在 0.7 秒得到 y≈20，变换均为有限数值；误写为四个数值时 y 变成 NaN。旋转从 0 到 30 度，在 0.7 秒使用 `value` 得到 21 度，使用 `angle` 则仍为 0。这里验证的是解析行为，不是该仓库全部动画或 Reskin 功能。[官方 4.2 解析器](https://github.com/EsotericSoftware/spine-runtimes/blob/4.2/spine-ts/spine-core/src/SkeletonJson.ts)

本项目当前按 60 FPS 烘焙骨骼采样，再交给运行库逐键线性插值。以后改成较稀疏的贝塞尔关键帧时，必须保留明确的格式转换层，并验证非零起始时间、负值、常值通道及循环边界，不能直接粘贴通用 CSS 缓动数组。

### 16.3 不能照搬的部分

以下均针对上面固定提交，区分仓库说明与实际实现：

- **不是一条无需补齐数据的命令链。** `position_parts.py` 输出 `parts/z_order/canvas_width`；`build_spine_json.py` 输入却要求 `bones/slots/attachments`。两者之间仍要决定关节位置、父子关系、附件偏移和命名映射。预设也依赖 `torso`、`right-upper-arm` 等特定骨骼名；惠惠的 `chest/upper_r` 等必须显式映射。
- **自动定位针对近似同视角素材。** 代码拒绝旋转绝对值大于 20° 的匹配，模板回退只搜索缩放和平移。调低 Lowe ratio 会更严格，不是放宽匹配；不能为了让每个部件“都有结果”而降低质量门槛。比较图和遮挡分析还只是按估计包围盒缩放贴图，没有完整应用估计旋转。
- **遮挡排序只是建议。** README 描述拓扑排序，实际 `compute_z_order` 按像素投票累计出的深度分数排序。它不能保证消除矛盾遮挡关系，也不代表转身时的动态绘制顺序。惠惠仍需单独编辑和检查 `drawOrder` 时间线。
- **父子坐标不能普遍直接相减。** 模板的 `child_world − parent_world` 仅在父节点没有旋转、缩放等变换时成立。一般情况应把世界点乘以父节点世界变换的逆矩阵；加权网格还必须在对应姿势绑定。
- **模板片段和预设描述有版本滞后。** 模板里的归一化 `curve` 示例与已修正的 4.2 导出脚本不同；README 写 idle 2.0 秒，`gen_idle` 实际是 1.6 秒。以固定版本源码、正式导出和运行库采样为准，不能把“用贝塞尔”当成自然动作保证。
- **自动分件会损失细节。** `split_character.py` 以灰度阈值和连通域取部件，存在把白色绷带、眼白和细小饰物当成背景或碎片的风险。生成分件不是恢复被遮挡部位的保证，仍须补画关节遮挡余量，并按第 4.1 节检查原图。
- **换皮功能需要多姿势验证。** 当前 `skin_writer` 的取样逻辑只取槽位首个附件，不能直接覆盖惠惠的多角度附件体系；Reskin 管线还可能缩放生成结果到预期尺寸。换皮后必须核对每个附件、UV、裁切偏移、alpha 和所有动作，不能仅验一张站姿。README 的快照切件叙述也与当前 `atlas/exploded` 两种管线不完全一致。
- **“素材内嵌”不等于完全离线。** 预览生成器内嵌图片与数据，但仍从 CDN 加载 `4.2.*` 播放器。项目交付继续使用本地固定版本运行库，并实际验证离线加载。

仓库标注的许可证是 [PolyForm Noncommercial 1.0.0](https://github.com/GenielabsOpenSource/spine-animation-ai/blob/702b71689cac826efee942ee4564fef9560d6ef8/LICENSE)。本轮仅整理方法；若以后引入其代码，应单独记录来源和许可，不能按 MIT 依赖处理。

### 16.4 转成当前项目可执行的制作约定

后续每个动作任务至少写清楚：输入骨架版本与素材、开始/结束姿势、动作意图、阶段和预计时长、停顿/经过姿势、支撑与握持约束、需补的透视图、允许修改的槽位，以及输出和验收方式。针对当前问题可使用以下任务描述：

> 修正 `chant_enter` 的逐姿势停顿。保留角色身份、右手固定握点和法杖刚体尺寸，明确经过姿势及真正收住的位置；先完成头、胸、骨盆和持杖手的主动作，再处理披风与帽尖。逐个检查附件切换轮廓。交付时间表、修正记录、固定相机轨迹图和游戏原速前后对比；如需新绘图，先保存原图并执行去 AI 摩尔纹流程，再切图绑定。

修正记录沿用“原值 → 增量 → 最终值”的思想，并增加 `clip`、`time_range`、`pose`、`slot/attachment`、`coordinate_space`、`source_sha256`、`reason` 和 `evidence`。每轮以明确版本为基准，避免重复叠加偏移。对加权网格，记录绑定姿势、顶点或权重修改；不要伪装成一个普通附件偏移就能表达的修改。

落地优先级：先用这些方法修正一个可对照的吟唱进入动作，验收节奏、弧线、体积与换图；再扩展至脱力和起身。自动部件定位、换皮服务和更复杂的生成工具按实际需要引入，不能替代主动作的设计与原速验收。本轮完成的是资料整理和诊断，v8 动画数据尚未据此重做。
